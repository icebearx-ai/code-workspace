# 基于 AI Coding 的团队经验知识库

## 提案状态

- 状态：Draft
- 关注点：降低疑难问题经验的记录成本，并让 AI 能够安全、准确地发现和复用团队经验
- 适用范围：由 Code Workspace 管理的本地 Agent Workspace、配套 Skill、MCP adapter 与独立团队知识服务

## 摘要

项目开发中存在一类公开网络难以回答的问题：它们带有复杂历史、内部基础设施、跨团队约束、特殊版本组合或隐含业务约定。团队成员可能曾经解决过这些问题，但依赖口头交流和事后文档无法稳定沉淀，人员流动后经验容易丢失。

本提案利用 Code Workspace 的可信内置 extension 能力，为不同 Agent 一致地安装记录 Skill、检索 Skill、本地 MCP adapter 和 Agent 配置。开发者解决问题后主动发起记录，AI 根据当前上下文生成结构化草稿，经过本地脱敏、重复检查、完整预览和开发者确认后提交。独立后台服务负责知识持久化、权限、审计、版本、混合检索、生命周期和贡献计算，MCP 仅作为 AI 面向的接入协议。

本系统不是传统 Wiki，也不是“上传 AI 聊天记录并做向量搜索”。它的核心知识单元是带有适用边界和验证证据的“经验案例”。搜索展示、AI 引用、开发者尝试和实际确认有效必须作为不同事件记录；首期只进行影子贡献计算，不直接接入月度绩效。

## 背景与问题

AI Coding 可以解决大量通用编程问题，但对以下问题通常缺少必要上下文：

- 公司内部系统的历史行为和特殊约定；
- 多个团队之间形成但未正式文档化的接口边界；
- 特定版本、环境、部署方式共同触发的问题；
- 错误信息表面含义与真实原因不一致的历史缺陷；
- 已经尝试过但被证明不适用的常见解决路径；
- 需要结合内部工单、日志、提交或事故复盘才能理解的结论。

开发者之间直接交流可以临时解决问题，但不能抵抗人员流动和时间衰减。要求每个开发者事后编写完整文档，在快节奏开发中也很难持续执行。即使建立普通知识库，仍容易出现以下问题：

- 记录成本高，开发者只在强制要求下提交；
- 内容缺少版本、环境和适用范围，后续使用时容易误导；
- 原始 AI 会话包含大量试错、源码、凭证或客户信息；
- 知识长期只增不减，过期内容逐渐污染搜索结果；
- AI 能召回文本，却无法判断是否适用于当前项目；
- 简单按引用次数奖励，会产生灌水、拆分、互刷和署名争议。

因此需要解决的不是“如何保存更多文档”，而是如何形成如下闭环：

```text
低成本生成候选经验
  → 人确认事实与授权
  → 服务端治理和发布
  → AI 基于当前上下文检索
  → 开发者实际验证
  → 反馈更新质量与生命周期
  → 对真实贡献进行可审计归属
```

## 核心判断

### 方案具备可行性

Code Workspace 当前 Extension Spec 已能通过通用输出安装完整文件、目录、共享文本块和共享 JSON 成员，因此可以承载：

- Codex 和 Claude 的记录/检索 Skill；
- 本地 MCP adapter runtime；
- Codex `.codex/config.toml` 中的 MCP 配置块；
- Claude `.mcp.json` 中的 MCP server 成员。

基础版本可以复用现有 extension 安装、升级、漂移检查、回滚和卸载能力，不需要为了团队知识业务修改 Host 公共协议。

### extension 只是分发与接入基座

extension 子进程不是安全沙箱，Code Workspace Host 也不负责管理扩展运行后产生的业务数据。因此以下职责不能放入 Host 的 extension 状态：

- 经验正文和 revision；
- 用户身份、团队权限和密级；
- 审核、发布和失效状态；
- 搜索索引、Embedding 和反馈事件；
- 贡献计算和月度统计；
- 真实 Token、Cookie 或长期用户凭证。

这些内容必须由独立团队知识服务治理。卸载本地 extension 只移除本地 Skill、adapter 和配置，不删除远程知识或审计数据。

### 奖励不能建立在引用次数之上

以下事件不能视为同一件事：

```text
搜索结果中出现
≠ AI 打开条目
≠ AI 引用条目
≠ 开发者尝试方案
≠ 方案实际解决问题
```

引用次数主要反映检索排序和问题热度，不足以证明知识质量。权威贡献规则必须由服务端版本化执行，Skill 只能解释规则、收集反馈和展示结果，不能在客户端自行计算绩效分数。

## 目标

本提案具有以下目标：

- 让开发者在问题解决现场以较低成本生成可审核的经验草稿；
- 保留开发者对上传内容、敏感信息、署名和最终提交的控制权；
- 只将有结论、有证据、有复用边界的内容发布为可执行经验；
- 允许记录有价值的失败路径和调查结论，但与已验证方案明确区分；
- 让 AI 综合错误码、项目、模块、版本、环境和语义相似度发现知识；
- 在结果中展示命中原因、适用条件、最后验证时间、状态和证据；
- 确保未授权知识不会通过标题、摘要、数量或向量召回泄漏；
- 通过实际使用反馈维护知识质量、发现失效内容并产生可审计的贡献归属；
- 以试点数据验证复用成功率和问题解决时间，而不是追求条目数量。

## 非目标

第一阶段不试图解决以下问题：

- 自动上传全部 AI Coding 会话；
- 将任意公开编程知识复制到内部知识库；
- 在没有证据和审核的情况下自动发布 AI 生成内容；
- 建立任意第三方 extension 市场或执行不可信扩展；
- 让 Code Workspace Host 理解知识、评分或远程存储业务；
- 用单纯向量相似度替代权限、版本和适用性判断；
- 根据展示或引用次数直接产生个人绩效分；
- 首期自动写入正式月度绩效系统；
- 由 extension 卸载流程删除用户产生的远程业务数据；
- 一开始引入知识图谱、独立向量平台或复杂推荐系统。

## 设计原则

### 原则 1：AI 降低记录成本，人确认事实和授权

AI 可以读取当前会话中已经出现的问题、错误、分析过程和验证结果，生成结构化草稿；但不能未经用户确认自动提交，也不能默认上传原始会话。

### 原则 2：事实、假设和调查结论必须区分

经验案例需要明确标识：

- 已验证解决方案；
- 部分有效方案；
- 调查结论；
- 已排除路径；
- 尚未验证的假设。

未经验证的假设可以保存在草稿中，但不能以已验证方案进入普通搜索结果。

### 原则 3：适用边界是知识正文的一部分

只记录“执行什么命令”是不完整的。项目、组件、版本、环境、前置条件、不适用条件、风险和回滚必须与解决步骤一同保存。

### 原则 4：知识必须可失效、可替代、可追溯

已发布 revision 不原地覆盖。修订产生新 revision，旧 revision 保持可引用，并通过 `supersedes` 关系被替代。每条知识都需要维护人、最后验证时间和复查时间。

### 原则 5：权限在召回前生效

权限过滤必须进入检索查询。禁止先对全部知识召回或生成摘要，再在结果层隐藏未授权条目。

### 原则 6：反馈用于质量治理，奖励是后置结果

先验证反馈是否可信、检索是否有效，再讨论绩效。奖励规则不能反过来驱动知识模型设计。


## Skill 边界

### 记录 Skill

建议名称：

```text
code-workspace-team-knowledge-record
```

只在用户明确要求记录、补充或修订团队经验时使用。其职责为：

1. 确认当前问题已经得到解决或形成有边界的调查结论；
2. 提取项目、模块、分支、错误码、依赖版本和验证结果；
3. 将原始上下文整理为结构化经验草稿；
4. 识别并删除凭证、个人信息、客户数据和无关源码；
5. 查询相似条目，提示新建、补充验证或提出 revision；
6. 展示最终 payload、署名、可见范围和证据；
7. 在开发者明确确认后调用写入工具。

Skill 不得：

- 自动上传完整会话；
- 未经确认代表用户提交；
- 把 AI 推测包装成已验证事实；
- 在本地计算权威贡献分；
- 自动扩大学科、项目或团队可见范围。

### 检索 Skill

建议名称：

```text
code-workspace-team-knowledge-search
```

在以下情况执行只读搜索：

- 用户明确要求查询团队经验；
- 问题包含内部错误码、内部服务、跨团队依赖或历史约定；
- 常规源码分析和公开资料无法解释当前事实；
- 当前问题与已知高成本故障类型相符。

Skill 应先形成问题指纹，再执行搜索。服务不可用、认证失败和搜索成功但无结果必须使用不同结果，不得将空输出或错误解释为“没有知识”。

## 哪些问题需要记录

一个可发布经验至少需要同时满足：

1. 已形成解决结论或有明确边界的调查结论；
2. 存在验证证据；
3. 能说明适用范围和不适用范围；
4. 已通过敏感信息和权限检查；
5. 已处置重复条目。

在此基础上，符合以下任意一项时具有较高记录价值：

- 公开网络难以找到正确答案；
- 带有公司、团队、项目或历史背景；
- 曾经重复出现或预计可能再次出现；
- 排查耗时较长，涉及多人或多个团队；
- 常规错误信息或文档会引导开发者走向错误结论；
- 方案具有严格顺序、风险、副作用或回滚要求；
- 常见失败路径及其排除证据具有复用价值；
- 影响生产、交付、安全或关键业务流程。

通常不应记录：

- 官方文档可以直接查到的通用知识；
- 简单语法、格式、拼写或普通编译错误；
- 未经验证的 AI 推测；
- 完整原始聊天记录；
- 只对一次性临时数据有效的处理；
- 已经由稳定项目文档完整覆盖的内容；
- 无法获得授权的跨团队或客户内容；
- 包含真实凭证且无法安全脱敏的内容。

## 经验案例模型

建议使用稳定 `caseId` 和不可变 `revision`。示意结构如下：

```json
{

  "caseId": "knowledge-case-uuid",
  "revision": 3,
  "type": "verified-solution",
  "title": "内部服务在特定版本下返回误导性 404",
  "problem": {
    "symptoms": "...",
    "errorCodes": ["INTERNAL_ERROR_CODE"],
    "keyLogs": ["..."],
    "components": ["service-a", "gateway-b"]
  },
  "applicability": {
    "workspace": "workspace-name",
    "projects": ["project-a"],
    "modules": ["module-x"],
    "branches": ["release/*"],
    "versions": {
      "service-a": ">=1.2 <1.4"
    },
    "runtime": ["node-20", "linux"],
    "requiredConditions": ["..."],
    "excludedConditions": ["..."]
  },
  "experience": {
    "background": "...",
    "hiddenConstraints": ["..."],
    "decision": "...",
    "steps": ["..."],
    "failedPaths": [
      {
        "attempt": "...",
        "whyItFailed": "...",
        "evidence": "..."
      }
    ],
    "risks": ["..."],
    "rollback": ["..."]
  },
  "verification": {
    "summary": "...",
    "evidenceRefs": ["test://...", "jira://...", "commit://..."],
    "verifiedAt": "..."
  },
  "governance": {
    "visibility": "team",
    "status": "verified",
    "maintainer": "user-id",
    "reviewAt": "...",

  },
  "contributors": [
    { "userId": "...", "role": "solver" },

  ]

```

### 必须结构化的字段

- 问题指纹；
- 适用项目、模块、版本和环境；
- 解决结论或调查结论类型；
- 验证摘要和证据引用；
- 适用与不适用条件；
- 风险和回滚；
- 可见范围和贡献角色；
- 状态、最后验证时间、维护人和复查时间。

正文允许使用 Markdown，但不能只保存一段无法过滤、无法判断适用性的自由文本。

## 生命周期

```text
DRAFT
  │ 提交审核
  ▼
IN_REVIEW
  │ 证据、边界、权限和查重通过
  ▼
PUBLISHED
  │ 独立使用者确认有效
  ▼
VERIFIED

PUBLISHED / VERIFIED
  ├────────复查期限到达────────▶ REVIEW_DUE
  ├────────确认已经无效────────▶ DEPRECATED
  └────────新 revision 替代────▶ SUPERSEDED
```

普通检索默认只返回 `PUBLISHED`、`VERIFIED` 和尚未被确认失效的 `REVIEW_DUE` revision。`DRAFT` 和 `IN_REVIEW` 仅对作者、审核者和授权治理人员可见。

`REVIEW_DUE` 仍可返回，但必须降低排序并明显提示复查状态。`DEPRECATED` 和 `SUPERSEDED` 不作为默认建议，仅在解释历史或显式查询时返回，并指向替代 revision。

## 记录流程

```text
开发者解决问题
  → 明确调用记录 Skill
  → AI 提取结构化候选
  → 本地敏感信息检查
  → 查询相似经验
  → 选择新建 / 补充验证 / 提出 revision
  → 展示完整预览、署名和可见范围
  → 开发者明确确认
  → MCP adapter 提交草稿
  → 服务端再次校验、审计和查重
  → 审核并发布
```

开发者取消确认时，不得产生远程草稿或贡献事件。服务不可用时，Skill 可以将结构化草稿展示给用户以便稍后重试，但不默认在 Workspace 中持久保存可能包含敏感内容的本地队列。

## MCP 工具合同

MCP 是 Agent 面向的适配层，不是团队知识服务的唯一接口。首期建议只提供以下工具。

### `team_knowledge_search`

输入：

- 自然语言问题；
- 错误码和关键日志；
- Workspace、项目、模块、分支和版本上下文；
- 运行环境；
- 返回数量和可选状态过滤。

输出：

- 查询状态：成功、无结果、服务不可用、认证失败或参数错误；
- 已授权的候选条目；
- 稳定 `caseId/revision`；
- 命中原因；
- 适用与不适用条件；
- 状态和最后验证时间；
- 证据摘要和稳定引用。

### `team_knowledge_get`

按 `caseId` 和可选 revision 读取完整授权内容。未指定 revision 时返回当前有效 revision，但响应必须明确实际 revision，避免引用随时间漂移。

### `team_knowledge_propose`

在用户确认后：

- 创建新草稿；
- 为已有案例补充独立验证；
- 提出新 revision；
- 记录解决者、记录者和来源；
- 携带幂等键避免重试产生重复条目。

该工具不得直接把普通用户提交变为 `PUBLISHED` 或 `VERIFIED`，除非服务端策略明确允许并记录对应审核事实。

### `team_knowledge_report_outcome`

报告一次实际使用结果：

```text
helpful
partially_helpful
not_applicable
failed
stale
```

响应需要记录使用的 revision、当前问题指纹、用户确认和可选验证证据。AI 自行判断“看起来解决了”只能形成候选反馈，不能直接形成正式贡献事实。

### 治理接口

审核、发布、失效、替代、归属争议、规则管理和批量运营不默认暴露给普通 Agent。它们通过独立管理 API、CLI 或管理界面完成，并使用更严格的角色权限。

## 检索与发现

单纯向量检索不足以解决内部疑难问题。建议检索流程为：

```text
身份与 ACL 过滤
  → 精确错误码、日志和关键词召回
  → 项目、模块、版本、环境过滤
  → 语义向量召回
  → 适用性、质量、新鲜度和独立验证重排
  → 返回 Top 3～5 个可解释候选
```

### 权限过滤

权限至少需要支持：

- 租户或组织；
- 团队；
- 项目；
- 密级或受限人群；
- 作者和审核者草稿权限。

未授权条目不能通过标题、摘要、Embedding、命中数量、错误差异或“存在但无权访问”的提示泄漏。

### 查重

查重同时使用：

- 稳定错误码和问题指纹；
- 项目、组件和版本边界；
- 语义相似度；
- 解决决策和关键步骤。

查重结果只提供候选。不同版本或不同适用边界下的相似问题不能由服务自动合并，应由记录者选择：

- 补充现有案例；
- 增加一次独立验证；
- 提出新 revision；
- 新建独立案例并建立关联。

### AI 使用规则

AI 返回建议时必须：

- 引用 `caseId/revision`；
- 说明为什么命中；
- 对比当前环境与适用条件；
- 提示版本、最后验证时间和复查状态；
- 区分知识中的事实、历史结论和当前推断；
- 在执行有风险步骤前保留现有确认和权限流程；
- 不把高相似度等同于可直接执行。

## 反馈与贡献机制

后台至少区分以下事件：

| 事件 | 含义 | 首期贡献处理 |
|---|---|---|
| `search_impression` | 条目出现在候选列表 | 不计分，仅用于检索分析 |
| `case_opened` | AI 或用户读取条目 | 不计分 |
| `use_attempted` | 开发者实际尝试方案 | 待验证 |
| `outcome_helpful` | 用户确认实际有帮助 | 进入贡献候选 |
| `outcome_partial` | 部分步骤或分析有效 | 较低权重候选 |
| `outcome_not_applicable` | 当前边界不匹配 | 更新适用性，不惩罚作者 |
| `outcome_failed` | 尝试后没有解决 | 进入质量复查 |
| `outcome_stale` | 内容已过期或被替代 | 触发生命周期治理 |
| `maintenance_verified` | 维护人完成复查或修订 | 维护贡献候选 |

贡献价值可以近似理解为：

```text
独立确认有效
× 实际影响权重
× 跨团队复用系数
× 新鲜度与维护系数
```

但正式算法必须由服务端配置、版本化和审计，而不是固定在 Skill 文本中。

### 贡献归属

需要分别记录：

- `solver`：实际解决问题的人；
- `recorder`：将经验整理并提交的人；
- `reviewer`：验证事实、权限和表达的人；
- `maintainer`：后续复查、纠错和修订的人。

记录者不能自动获得解决者的全部贡献。AI 不作为作者。条目从其他团队、事故复盘或工单整理而来时，必须保留原始来源和参与者。

### 防刷规则

- 搜索展示和引用不直接计分；
- 自己不能独立确认自己的方案有效；
- 同一用户、同一问题指纹和短时间重复反馈去重；
- 同一团队对同一 revision 的重复成功反馈设置递减或上限；
- 跨团队独立验证具有更高可信度，但必须通过权限和真实性校验；
- 内容被确认不适用不直接处罚作者，只有恶意灌水、伪造证据或拒绝纠错进入治理流程；
- 评分结果必须能追溯到规则版本、输入事件和归属分配。

### 影子计分

首期可以计算贡献结果并向治理人员展示，但必须标记为 `shadow`：

- 不写入正式绩效系统；
- 不直接形成个人月度排名；
- 用于发现算法偏差、热门问题垄断、新员工劣势和互刷模式；
- 只有在试点数据证明有效后，才通过独立提案讨论正式绩效集成。

## 安全与隐私

### 提交前本地检查

记录 Skill 需要检查并提示：

- Token、Cookie、密码、私钥和连接串；
- 客户名称、电话号码、身份证、邮件等个人信息；
- 未经授权的源码片段、数据库记录和生产日志；
- 内部地址、工单或附件是否允许跨团队共享；
- 署名和来源是否准确。

本地检查是降低风险的交互措施，不是安全边界。服务端必须再次校验。

### 服务端控制

- 组织身份认证和最小权限；
- 写入、读取、审核和治理角色分离；
- 字段级敏感信息检测；
- ACL 在召回前生效；
- 所有读取、写入、状态和贡献变更可审计；
- revision 保留，但依法或按安全要求支持受控删除和索引清理；
- 日志、Embedding 输入和诊断不得包含未经授权的秘密；
- 错误响应不泄漏未授权条目存在性。

### 凭证边界

extension manifest、installed 状态、Skill 和静态 MCP 配置中不得包含真实长期凭证。adapter 应从批准的组织登录、短期令牌或企业凭证代理获取身份，具体方式需要在实施前确认。

## 服务端建议边界

建议将后台分为以下领域模块：

```text
identity-access
case-revision
review-lifecycle
content-policy
deduplication
hybrid-search
usage-feedback
contribution-ledger
audit-governance
```

MVP 可以使用关系数据库保存结构化事实、revision、ACL 和事件，并结合全文检索与向量扩展完成召回。暂不引入知识图谱和独立向量基础设施，除非真实规模和查询证明必要。

## 分阶段落地

### 第一阶段：知识合同与种子数据

- 固化经验案例 schema、状态机、权限范围和错误合同；
- 明确“可发布”“已验证”和“贡献有效”的证据标准；
- 准备一批已经确认的高价值历史案例；
- 确认后台服务负责人、认证方案和部署边界；
- 建立 MCP adapter 与后台 API 的契约测试。

这一阶段不开发奖励榜，不接入绩效。

### 第二阶段：最小记录与检索闭环

- 发布可信内置 `team-knowledge-base` extension；
- 安装 Codex/Claude record Skill、search Skill、adapter runtime 和 MCP 配置；
- 实现 `search`、`get`、`propose` 和 `report_outcome`；
- 实现本地预览、脱敏、查重提示和显式确认；
- 实现服务端草稿、审核、发布、revision、ACL、审计和基础混合检索；
- 搜索和反馈失败不阻断 Code Workspace 核心操作。

### 第三阶段：生命周期与质量反馈

- 引入独立验证、复查期限、失效和替代；
- 优化适用性重排和重复检测；
- 建立错误知识的纠错、争议和维护流程；
- 度量 Top 3 有帮助率、复用成功率和解决时间变化；
- 评估开发者完成一次记录的平均成本。

### 第四阶段：影子贡献

- 引入服务端规则版本和贡献账本；
- 区分解决者、记录者、审核者和维护者；
- 实施事件去重、同团队上限和异常检测；
- 运行至少一个完整评价周期但不影响正式绩效；
- 根据偏差和行为变化决定是否需要继续、调整或停止奖励机制。

### 第五阶段：是否正式激励

只有同时满足以下条件时，才另行讨论正式激励：

- 有效反馈具有足够真实性和覆盖率；
- 错误或失效知识比例处于可接受范围；
- 没有明显灌水、拆分、互刷和署名争议；
- 新人、维护者和处理冷门高价值问题的人没有系统性劣势；
- 贡献结果可以解释、复核和申诉；
- 团队确认它只作为综合评价的参考，而不是单一排名依据。

## 验收标准

第一版至少应覆盖以下场景：

1. extension 能通过现有 Spec v1 能力安装和卸载两个 Skill、adapter runtime 及 Codex/Claude MCP 配置，不修改 Host 公共协议；
2. 卸载本地 extension 不删除远程经验、审计和贡献数据；
3. 用户未明确确认时，record Skill 不调用远程写入；
4. record Skill 不上传完整原始会话，只提交预览中展示的结构化字段；
5. 检测到凭证或受限数据时，提交被阻止并给出可执行脱敏建议；
6. 服务端对客户端提交再次执行认证、授权和内容策略校验；
7. 相似案例存在时，用户可以选择补充验证、提出 revision 或独立新建，服务不自动错误合并；
8. 已发布 revision 保持不可变，修订产生新 revision，引用能够稳定定位历史内容；
9. 未授权条目不会通过搜索结果、摘要、命中数量或错误差异泄漏；
10. 精确错误码和结构化版本条件可以优先于纯语义相似结果；
11. AI 返回知识时展示命中原因、适用边界、状态、最后验证时间和稳定引用；
12. 服务不可用、认证失败、成功但无结果使用不同的结构化结果；
13. `DRAFT` 和 `IN_REVIEW` 不进入普通用户默认搜索；
14. `REVIEW_DUE` 明显提示并降低排序，`DEPRECATED` 和 `SUPERSEDED` 不作为默认执行建议；
15. 搜索展示和 AI 引用不会直接产生正式贡献；
16. 用户确认且符合证据标准的实际使用结果才能进入贡献候选；
17. 同一用户和同一问题的重复反馈被去重；
18. 贡献结果可追溯到 revision、反馈事件、规则版本和角色归属；
19. 第一阶段的贡献结果标记为 shadow，不能写入正式绩效系统；
20. 知识服务故障不阻断 Code Workspace 核心 `init`、`update`、项目管理和其他 extension 的正常行为。

## 评估指标

核心指标：

- 搜索 Top 3 中被确认有帮助的比例；
- 被其他开发者或团队独立验证成功的比例；
- 相同类型问题平均解决时间是否下降；
- 错误、失效和被替代知识的比例；
- 重复条目比例；
- 从问题解决到完成草稿提交的平均耗时；
- 从草稿到发布的审核时长；
- 贡献者、维护者和使用团队的分布是否过度集中。

不应作为主要成功指标：

- 知识条目总数；
- AI 搜索次数；
- 条目展示次数；
- 条目引用次数；
- 单纯的个人积分总量。

## 风险与权衡

### 记录意愿不足

即使提供 Skill，开发者仍可能不愿在问题解决后继续操作。需要让 AI 复用当前上下文、生成短而完整的草稿，并控制必填字段和交互步骤。是否实用应以真实记录耗时和完成率验证。

### AI 生成的内容看似完整但事实错误

结构化输出不能替代事实验证。发布门槛、证据、用户确认、领域审核和独立使用反馈必须共同工作。

### 陈旧知识污染检索

如果只有新增奖励而没有维护奖励，系统必然退化。必须把复查、纠错、失效和替代作为一等能力，并给予维护贡献。

### 奖励扭曲行为

绩效激励会使参与者优化计分规则，而不一定优化团队价值。影子计分、事件去重、上限、独立验证和申诉机制只能降低风险，不能完全消除风险。

### 热门问题垄断贡献

高频但简单的问题可能积累大量反馈，而冷门但关键的问题价值更高。贡献规则需要考虑影响、跨团队复用和维护，而不是累计次数。

### 权限与搜索冲突

更严格的权限会降低跨团队发现能力，更开放的权限会增加泄漏风险。默认可见范围、跨团队审核和受限知识摘要策略需要在实施前明确。

### 服务端不在当前仓库

Code Workspace 可以交付 extension 和接口适配，但独立后台服务需要明确代码库、所有者和发布节奏。没有服务端负责人时，不应先实现只有客户端的半套功能。

## 开放决策

进入实现前仍需确认：

- 团队知识后台服务由哪个团队和代码库负责；
- 服务部署是组织级、部门级还是团队级；
- 默认可见范围是项目、团队还是组织；
- 跨团队内容由谁审核，审核 SLA 是多少；
- 本地 MCP adapter 使用何种组织认证和短期凭证；
- 哪些证据可以自动判定有效，哪些必须人工确认；
- 经验案例默认复查周期如何按类型配置；
- 是否允许复制内部日志或源码片段，允许到什么粒度；
- MVP 是否需要管理界面，还是先提供受限管理 CLI/API；
- 贡献角色如何分配权重，同团队重复使用如何衰减；
- 影子计分需要运行多久、达到哪些指标后才允许讨论绩效集成；
- 知识删除、人员离职、团队迁移和项目归档时如何保留来源与重新分配维护责任。

## 结论

本方案的技术基座是可行的：Code Workspace extension 可以稳定分发 Skill、MCP adapter 和 Agent 配置，独立服务可以完成知识存储和调用。但真正决定系统能否长期有效的，不是 MCP、向量数据库或积分榜，而是以下闭环：

```text
结构化经验
+ 明确适用边界
+ 可验证证据
+ 人工确认与审核
+ 权限过滤
+ 稳定 revision 引用
+ 实际使用反馈
+ 失效与维护机制
```

因此建议先建设“证据化经验记录与检索闭环”，暂不把奖励机制作为 MVP 的核心验收项。只有知识质量、检索有效率和反馈真实性得到验证后，影子贡献才有资格进一步成为月度评价的参考。
