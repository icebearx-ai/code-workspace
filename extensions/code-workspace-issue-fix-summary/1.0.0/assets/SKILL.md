# 问题修复总结

用于一个问题已经处理完成后的收尾动作：从当前 agent 会话提取证据，生成修复总结；只有经过明确确认，才可以通过已安装的 `zhuiyi-jira-mcp` 发布到 Jira 工单评论。

## 调用边界

- 这是主动调用型 skill。只在用户显式调用 `$code-workspace-issue-fix-summary`（或明确要求使用本 skill）时运行，不要因“修复完成”“提交代码”等普通消息自动触发。
- 总结阶段只读取当前会话及用户随后补充的材料，不执行 Jira 写入。
- Jira 写入是外部副作用，必须同时满足“总结文本已确认”和“目标工单 URL 已确认”两个条件；不能把含糊的“好的”“可以”当成对未展示内容的授权。

## 工作流

### 1. 收集证据

优先从当前会话中整理：问题现象、定位过程、根因证据、实际修改的文件/逻辑、测试或验证结果，以及 Jira 工单 URL。区分“已证实事实”和“推测”，不要把猜测写成根因，也不要把计划中的改动写成已完成改动。

如果会话不足以同时支持根因和修改内容两部分：暂停生成结论，向用户索取对应的 project 标识（名称或绝对路径）和 commit（优先完整哈希）。不要猜测项目路径、分支或提交；用户补充后，只检查其明确指定的项目和提交，并以提交差异、提交说明及会话证据为依据。

### 2. 生成待确认文本

有足够依据时，输出一份可直接放入评论的中文草稿，严格使用以下结构（保留两个标题和编号列表；按实际条目增减，不要虚构空项）：

```
根因：
1. xxx。
2. yyy。
......

修改内容：
1. zzz。
2. ddd。
```

“根因”写导致问题发生的底层条件或缺陷，而不是表面现象；“修改内容”写已经实施的代码、配置、数据、测试或文档变更。条目应具体、简洁，必要时带上文件、模块或行为范围。草稿后明确询问用户是否确认这份**完整文本**，并说明确认后仍需确认 Jira 目标。

如果证据仍不充分，不要用占位符或免责声明伪造总结；直接说明缺少哪类事实，并再次请求 project 与 commit 或必要的补充说明。

### 3. 确认并准备 Jira 目标

- 用户确认总结文本后，检查历史会话中是否有明确的 Jira 工单 URL。
- 没有 URL：要求用户提供要写入的完整 URL；在收到前不要调用 MCP。收到后，将该 URL 原样展示，并按下述规则再次取得发布确认。
- 有一个明确 URL：原样展示该 URL，并再次询问用户是否确认将刚才的已确认文本发布到该 URL。历史 URL 只能作为候选，不能视为本次授权。
- 有多个、截断、或看起来不确定的 URL：列出候选并要求用户给出/确认唯一目标。
- 如果用户修改了总结或更换 URL，视为新内容，重新取得相应确认。

### 4. 发布评论

确认文本和目标 URL 都明确后，检查当前工具环境是否提供 `zhuiyi-jira-mcp`。若未安装、未暴露可用方法或不可访问：告知用户暂时无法发布，并保留完整总结供其复制；不要声称已写入，也不要解释 MCP 的具体 API 用法。

若 MCP 可用，使用其提供的“向 Jira 工单添加评论”能力，遵循该方法自身的参数描述；评论正文使用用户确认的原文，不自行添加标题、签名或改写。调用失败时如实报告失败原因并保留文本，不要重复执行可能造成重复评论的写入，除非用户明确要求重试。

成功后仅报告已将评论写入用户确认的 URL；如工具返回评论地址或标识，可一并提供。
