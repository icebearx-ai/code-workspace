# Jira 需求分析

## 可用资料来源

遇到内部 Jira 链接时，使用 `zhuiyi-jira-mcp` 获取需求正文、评论、附件、关联任务和子任务等可访问内容。

设计稿可能是 Jira HTML 附件，也可能是 OpenSVN 页面；分别使用 `zhuiyi-jira-mcp` 和 `zhuiyi-opensvn-mcp` 获取。MCP 自身已经说明调用方法，本 Skill 不重复工具参数和操作步骤。

如果缺少对应 MCP，或调用因鉴权、权限、配置、网络等原因失败，直接告诉用户缺少了什么资料、会影响哪部分分析，并建议检查对应 MCP 的鉴权或配置。不要编造未取得的内容。

## 第一步：确认本次范围

先查看 Jira 是否包含子任务或明确的角色拆分，例如前端、后端、测试、产品或设计任务。

- 没有子任务或拆分时，默认分析整个需求。
- 有子任务时，先列出父任务和子任务的摘要、类型、状态及相互关系，让用户选择本次分析范围。
- 用户可以选择父任务整体、一个子任务或多个子任务。
- 用户确认前，不进入需求分析，也不读取代码。

后续分析严格限制在用户选择的范围内。其他子任务只在解释依赖、接口边界或跨端影响时引用，不扩展成本次执行范围。

如果所选任务依赖未选择的子任务，明确说明依赖和影响，由用户决定是否扩大范围、仅按接口假设分析，或暂停等待依赖明确。

## 第二步：分析需求本身

围绕“能否让开发和测试得到同一种理解”分析，不机械套模板。

重点检查：

- 需求要解决什么问题，目标用户和成功结果是什么。
- 本次范围的输入、触发条件、主流程和最终结果是否明确。
- 前置条件、状态变化、数据规则、权限规则和异常处理是否闭环。
- 前端、后端、测试等子任务之间的职责和交付边界是否一致。
- 验收标准是否具体、可观察、可测试，是否覆盖关键异常和边界。
- Jira 正文、评论、子任务和设计稿之间是否存在矛盾、遗漏或不同解释。
- 设计稿是否覆盖需求中的页面、状态和交互；静态设计无法证明的后端规则或动态行为要明确指出。

不要替产品补写业务规则，也不要把设计稿或某条评论自行认定为最终口径。

发现矛盾、歧义、不明确或缺失时，输出：

1. 问题是什么。
2. 相关证据分别怎么说。
3. 不同理解会怎样影响范围、实现或验收。
4. 需要用户决定的具体选项。

然后停止等待用户决策。只有用户明确给出口径，或明确允许按某个假设继续，才能进入代码可行性分析。

## 第三步：结合代码分析可行性

用户确认需求口径后，再确定并读取与本次范围对应的代码项目。受 Code Workspace 管理时，先遵守项目选择、定向验证和分支一致性规则；不要扫描或分析无关项目。

分析：

- 现有代码是否已经支持部分或全部需求。
- 需要修改或新增哪些模块、页面、接口、数据结构、权限、配置和测试。
- 所选前端/后端/测试范围与其他子任务之间有哪些接口和依赖。
- 是否存在架构限制、数据兼容、迁移、性能、安全或回归风险。
- 哪些结论有代码证据，哪些仍依赖产品、设计、后端或其他团队确认。

结论使用“可行 / 有条件可行 / 当前不可行 / 信息不足”，并给出主要依据、影响范围、风险和实施前置条件。

代码分析中再次发现需求与代码、设计或子任务定义冲突时，不自行选择方案；列出可选方案及影响，让用户决定。

## 输出要求

输出保持简洁，优先展示：

1. 用户确认的分析范围。
2. 已确认的需求理解。
3. 问题与风险。
4. 需要用户决定的事项。
5. 用户决策后的代码可行性结论。

明确区分资料中的事实、AI 的推断、暂用假设和未知信息。关键结论引用 Jira、设计稿或代码证据。

本 Skill 负责分析和决策准备，不直接实施代码变更。用户要求实施时，应在需求口径和执行范围已经确认后作为后续任务处理。
