# Jira 任务拆分

本 Skill 只处理用户明确调用的 Jira 任务拆分请求，不因普通需求分析、代码开发或 Jira 话题自动触发。可使用 `zhuiyi-jira-mcp` 获取需求正文、评论、附件、关联任务和子任务；MCP 自身已说明调用方法，本 Skill 不重复工具参数和操作步骤。

## 资料与分析规则

如果工作区存在 `zhuiyi-jira-prd-analysis`，本 Skill 的需求范围确认、需求澄清、证据区分、歧义升级和代码可行性分析均遵循该 Skill 的规则，并在其完成范围确认后继续任务拆分。若该 Skill 不存在，则撤回上述复用要求；本 Skill 仅依据当前可取得的需求事实进行拆分，不自行补充缺失的需求分析流程或业务规则。

优先通过 `zhuiyi-jira-mcp` 获取 Jira 需求及其相关资料。如果 `zhuiyi-jira-mcp` 不存在、不可访问、鉴权失败，或其能力不足以取得本次拆分所需的需求正文、范围、附件或关联信息，立即告知用户缺少的资料及其影响，请用户直接提供需求相关内容。用户未提供足够事实前，停止分析和拆分，不得根据标题、猜测或常见业务模式编造任务。

## 1. 确认分析范围

先确认 Jira 父任务/子任务范围；当 `zhuiyi-jira-prd-analysis` 存在时，遵循其范围规则：有子任务时列出摘要、类型、状态和关系，让用户选择父任务整体或一个/多个子任务；用户确认前不开始拆分。

同时确认拆分维度。有效维度只有【前端】【后端】【测试】，支持多选：

- 用户在调用 Skill 时已指定维度，直接采用。
- 未指定时，先询问用户选择一个或多个维度，再继续。

后续严格限制在用户选定的需求范围和维度内。引用未选范围只能用于说明依赖，并明确这是范围外依赖。

## 2. 分析并拆分

基于 Jira 正文、评论、附件、设计稿和已确认的范围，提炼可执行交付物、职责边界、接口依赖、验收关注点和风险。区分资料事实、合理推断、暂用假设和未知信息；遇到矛盾或关键歧义时列出证据、影响和待用户决定的选项，并暂停拆分。

任务拆分遵循以下粒度：

- 以中级开发工程师、在 AI 有限辅助下的实际工作量估算。
- 单个任务只能是 2h、4h 或 1d；不得大于 1d 或小于 2h。可将较大工作拆成多个任务，将过小工作合并到同一交付物。
- 任务应保持可独立理解和验收，避免按文件、函数或过细步骤机械拆分，也避免把多个明显独立交付物合成一个粗任务。

## 3. 输出格式

分析结果必须先以 Markdown 表格呈现，表头固定为：

| 编号 | 任务名 | 任务简介 | 工作量 |
|---|---|---|---|

内容格式要求：

- 每个任务名和简介都要体现选定维度；“任务名”统一以维度标签开头，例如“【前端】开发页面...”或“【后端】新增接口...”。
- “任务简介”尽量简要，写清交付内容和关键边界；
- “工作量”只填写 `2h`、`4h` 或 `1d`。按前端、后端、测试的选定顺序组织任务，并保证编号连续。表格后补充必要的依赖、假设、风险和总工作量。

## 4. 用户确认与 Jira 创建

表格和分析完成后，明确请求用户 check：请用户确认任务内容、维度、粒度和工作量。用户未明确同意前，不调用 MCP 创建 Jira 任务，也不把“看起来没问题”当作授权。

只有用户明确表示同意、确认、批准或要求创建后，才调用 `zhuiyi-jira-mcp` 按确认后的表格新增 Jira 任务。创建前若用户修改了任何任务，先更新表格并再次请求确认。创建完成后反馈 MCP 返回的任务标识和结果；部分成功时逐项说明成功与失败，不自行重试造成重复任务。

本 Skill 负责分析、拆分和获得创建前确认，不直接修改代码，也不替用户补写未确认的业务规则。
