# 研发过程关键环节检查点

适用：代码审查、评审、测试设计和上线前验证。按当前阶段读取对应章节，不要把全部检查项当成当前任务的强制工作量。

## 开发与代码审查

### 账务与防重

- 交易超时或未明时不得直接判定失败；必须先查证状态，之后才可续作、重试或冲正。
- 同一请求 ID 或业务数据重复调用时，结果和数据库状态必须一致，只产生一笔有效记录。
- 防重必须针对最终处理记录，状态设计包含中间态，不能只有“未处理/已处理”。
- 批量同时触发多个实例时，任务防重和交易防重都必须生效。
- 多系统链路由接入层、中间层、服务方分别防重。

### 批量文件批前校验

- 文件名称、格式、编码可正常读取；名称或格式失败应阻断并预警。
- 校验最小/最大文件大小、数据量、空文件和就绪标识文件。
- 校验关键字段唯一性、非空、字段数量和格式。
- 区分系统性风险校验和数据质量校验；阈值至少设置下限，上限或峰值预警按业务决定。

### 数据与 SQL

- 数据删除、迁移前备份并验证可用性，失败可回滚。
- 联机 SQL 的 `WHERE`、复合索引最左匹配和排序顺序必须与索引匹配。
- 使用 `EXPLAIN` 检查是否出现 `type=ALL`；大表和复杂 SQL 与 DBA 评审。
- 新增非空默认字段时，确认存量数据、读取逻辑、默认值/空值和表锁风险。
- 分区表查询必须包含分区键，定期重检表量和分区策略。
- Redis 必须可以重建且重建时间可控，模拟宕机验证降级，检查双写一致性。

### 代码健壮性

- 重点核对相似变量名，如 `userName`/`userNames`，以及复制粘贴代码块的上下文。
- 核对前端到后端字段大小写和命名差异。
- 对接口、数据库和文件中映射的定长字段显式判断长度并截断。
- 不依赖前端或调用方控制长度，防止入库失败、接口报错或文件格式错乱。

## 测试与上线前验证

### 文件异常

- 覆盖空文件、格式错误、大小异常、部分缺失、编码错误、数据量异常等场景。
- 确认异常有明确提示和日志，系统不崩溃，核心业务不中断。

### 业务场景

- 新流程覆盖主流程、分支流程和备选流程，如应急登录。
- 修改流程进行影响性测试；主干流程修改要覆盖其全部分支，不能只抽测部分路径。
- 测试案例对照详细设计逐项覆盖，不只验证正常路径。

### 测试数据

- 覆盖 `NULL`、空字符串、极值、特殊值和非法值。
- 数据应贴近生产真实情况，不能只用无业务意义的数据。
- 重要需求必要时使用脱敏后的生产数据进行验证，遵守数据安全要求。

### 环境与变更

- 扫描投产包，阻断开发、测试、localhost 的地址、账号、密码和路径。
- 验证业务全链路、批量跟批、定时任务和回滚方案。
- 检查变更审批、版本一致性和代码比对，确认没有夹带。
- 大表结构变更必须有 DBA 和应用管理员评审，以及窗口、耗时、锁表、回滚和影响分析。

## 完成条件

只有以下证据可获得时才声明对应检查通过：

- 代码或配置中的明确实现；
- 测试用例和实际执行结果；
- SQL 执行计划、日志、监控或批处理结果；
- 审批、演练或恢复记录。

缺少证据的项标记为“待确认”，不要用“已遵循规范”代替。
