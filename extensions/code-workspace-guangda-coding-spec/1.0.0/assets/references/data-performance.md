# 数据、性能、可用性与分区规范

适用：备份、文件/日志留存、Redis、SQL、索引、执行计划、大表、流控、故障隔离、降级、第三方依赖、分区和分表。

## 数据不能丢

**风险：高。检查手段：设计评审、非功能测试。**

- 关键业务系统必须满足数据库、业务文件和日志的备份要求，关键数据不可丢失。
- 非结构化数据长期在线存储应使用影像业务管理平台或对象存储。
- 历史数据应使用带库备份并签订备份协议，保留周期满足监管要求。
- 删除或迁移数据前先备份，验证备份可用，确保变更失败可回滚。
- Redis 只能作为缓存，禁止当作唯一存储；冷热数据分离，避免把全部数据放入 Redis。
- Redis 故障时应具备降级或替代访问手段；缓存数据应可重建且重建时间可控。
- 双写场景必须检查数据一致性，并模拟缓存宕机验证降级方案。

代码审查重点：数据库是最终事实源；缓存失效不会导致不可恢复的数据丢失；备份和恢复经过演练，不只停留在配置说明。

## 联机不能慢

**风险：高。检查手段：设计评审、非功能测试。**

- 联机交易 SQL 必须建立与查询逻辑匹配的索引，避免全表扫描。
- 查询条件左侧不得对索引列使用函数或运算表达式，避免索引失效。[OCR 原文写作“左边”]
- 注意类型隐式转换、`LIKE '%xx'` 左模糊、复合索引最左匹配和排序字段顺序。
- 对修改或新增的 SQL 使用 `EXPLAIN` 检查；大表或复杂 SQL 与 DBA 评审执行计划。
- Oracle 应定期收集统计信息；SQL 变更必须基于生产数据量评估执行计划变化。
- 单表超过 1000 万条或 4G 时必须分区或分表。
- 避免无查询条件限制的开放式 SQL 和大批量结果处理。
- 新增非空默认字段前评估存量数据、读写兼容、大表锁表和执行时长。

代码审查重点：高频 SQL 有索引；分区表查询包含分区键；生产数据规模下不会退化为全表扫描或超大结果集。

## 服务不能堵

**风险：高。检查手段：设计评审、非功能测试。**

- 不同业务或服务领域应解耦为独立模块，故障对象应能被隔离或关闭。
- 必须提供有效流控，至少覆盖交易级、渠道级、渠道加交易级。
- 慢交易应独立部署或隔离，避免占用正常联机交易资源。
- 隔离参数通过共享内存等动态方式加载生效，避免隔离操作本身导致重启或联机中断。
- 第三方接口要有针对异常、超时和不可用的有效阻断机制。
- 非关键业务应可降级，避免影响关键联机业务；优先使用总前或分布式平台的标准流控能力。

代码审查重点：并发突增可控、慢依赖不拖垮主链路、降级不会污染核心数据、回切过程可验证。

## 分区设计规范遵从

**风险：高。检查手段：详细设计评审、评审检查单。**

- 单表记录超过 1000 万条或 4G 时必须进行分区或分表；分区表查询必须包含分区键。
- Oracle 分区表不允许使用全局索引或非分区索引。[ORACLE-003]
- 按日期分区时预定义 MAX 分区并提前预置分区，避免无分区可落数据。
- 时间范围分区应为未使用分区统一导入统计信息：优先取最后一个有数据分区；数据不足时取数据量最大的分区。运行一段时间后收集历史分区统计信息还原真实值。
- MySQL 大数据表优先分表；不能分表时再使用分区。

代码审查重点：建表脚本含分区和 MAX 分区、索引为分区索引、统计信息策略明确、运维具备定期重检和扩展能力。
