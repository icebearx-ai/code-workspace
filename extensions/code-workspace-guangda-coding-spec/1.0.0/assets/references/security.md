# 开发安全十条红线

适用：认证授权、输入处理、页面输出、命令执行、文件上传、短信、配置和关键交易信息。

## 一、防止身份验证绕过和越权

- 所有身份验证必须在服务端等可信系统执行，禁止依赖浏览器 JS 校验验证码等客户端检查。
- 服务端记录验证状态；未完成前不得执行需要相应权限的操作。
- 多步骤交易每一步都记录并校验前一步已完成，防止跳过开户、实名或密码设置步骤。
- 账号增删、授权、业务操作和审批必须在服务端校验角色权限，防止垂直越权。
- 查询、转账、账号修改等重要操作必须校验用户与操作对象的关系，防止通过修改对象 ID 水平越权。
- 禁止预留后门文件；互联网系统内部管理账号不得使用弱口令。
- 验证码、短信、人脸识别等验证手段必须防止绕过。

验证重点：身份状态不可由客户端声明；管理、操作、审核、审计权限分离；对象级授权不能只依赖前端隐藏。

## 二、防止信息泄露

- Web 部署目录不得保留脚本、备份、源码、配置文件、`.svn` 等非发布文件。
- 对外文件不得包含内网 IP、内部数据注释等内部信息。
- 异常返回不得暴露详细报错、堆栈、SQL；应跳转统一友好提示。
- 正确配置 F5、Web 服务器和目录权限，禁止互联网浏览部署目录或任意文件下载。
- 不得在 GitHub、百度文库等外部平台留存代码或设计文档。
- 登录失败对“用户不存在”和“口令错误”返回一致且模糊的信息。
- 对外 API 按业务含义最小返回字段，禁止直接返回全表字段。
- 禁止非必要、未授权的后台管理页或 API 面向互联网开放。
- 敏感字段按全行统一标准屏蔽，避免多个功能点拼接出完整信息。

验证重点：错误响应、日志、静态资源、接口 DTO、部署产物和网络暴露面均遵循最小暴露原则。

## 三、防止 SQL 等注入

- 使用绑定变量、参数化预编译或存储过程，禁止拼接 SQL。
- 对输入做类型、字符范围和值域校验；数字校验每位字符和合法范围，字符串采用允许范围校验。
- 必须拼接时先按数据库语义转义，但不能把转义替代参数化。
- SQL、LDAP、OS 命令、XML、JSON 注入均需严格检查或上下文转义。
- 发现非法输入应拒绝并记录日志，建立统一过滤机制。

验证重点：搜索字符串拼接 SQL；ORM 的原生 SQL/排序/表名/字段名是否可被外部控制。

## 四、防止 XSS、CSRF

- 过滤或编码 `<`、`>`、引号、`script` 等可用于动态脚本的内容。
- 按输出位置进行 HTML、JavaScript 等上下文转义，防止用户内容作为脚本执行。
- 验证请求 `Referer` 可辅助防御 CSRF。
- CSRF 必须使用随机 token 校验，不能只依赖 Cookie 判断请求合法。

验证重点：富文本、URL 参数、路径参数和模板输出均编码；状态变更请求有 CSRF 防护。

## 五、防止远程命令执行

- 非必要不使用 `exec()`、`eval()`、`system()` 等动态执行方法。
- 使用这些方法时禁止动态拼接参数，并对命令及参数执行严格白名单校验。
- 输入校验必须覆盖命令分隔符、参数注入和路径逃逸。

验证重点：搜索命令执行、模板求值和动态代码执行入口，确认外部输入不能控制命令或代码。

## 六、正确配置应用系统

- Web 应用通常只允许 `GET` 和 `POST`，禁止 `TRACE`、`OPTIONS` 等不必要方法。
- 正确配置中间件，禁止部署目录可浏览或任意文件可下载。
- 禁止通过反向代理透传打通 DMZ 与内网。
- 互联网 HTTP/HTTPS 应用不得未经 WAF 防护直接暴露。

验证重点：检查容器、Nginx、Tomcat/Spring 等实际配置，不只看文档。

## 七、防止任意文件上传

- 只允许业务需要的文件类型，并校验扩展名与实际文件内容一致。
- 上传文件只能存入预期目录，使用服务端生成的文件名和扩展名。
- 如需保留原名，只在数据库中保存映射，不直接用原名落地。
- 可对落地文件编码，或纳入受控存储，防止恶意脚本直接执行。
- 限制文件大小，防止耗尽存储。
- 严禁上传 `.html`、`.jsp`、`.php`、`.cmd`、`.exec` 等可执行文件。

验证重点：文件头/魔数、双扩展名、大小写、路径穿越、压缩包、相对路径和存储目录执行权限。

## 八、防止暴力破解

- 图形验证码须由服务端生成和验证。
- 限制失败登录频次；连续失败后暂停登录一段时间。
- 同时按账号和 IP 控制尝试频次。

验证重点：验证码不可重复使用，失败计数不能只在客户端维护，锁定策略不会误伤或泄露账号是否存在。

## 九、防止短信炸弹

- 注册等非登录场景发短信前使用图形验证码，防止自动脚本。
- 限制发送频次，上一条发送后必须经过等待时间才能发送下一条。
- 已登录场景优先从预留信息获取手机号，非必须不得从前端接收。
- 必须接收前端手机号时，应验证其合法性。

验证重点：接口限流按手机号、账号、IP、设备和时间窗口组合生效，异常调用有告警。

## 十、防止关键交易信息篡改

- 金额、额度、单价、总价、收益率等关键字段从服务端获取，不能信任客户端提交值。
- 客户端返回后再次使用的信息必须加密或做完整性保护，服务端仍要重新校验。
- 互联网报文使用 SSL 通道；关键交易和个人敏感信息在通道加密基础上再加密。
- 行内应用交互遵守加密规范：
  - 客户账户密码产生、验证、传输调用 PIN 加密/转加密接口。
  - 资金、账务等敏感变更报文调用 MAC 或签名验签接口做完整性校验。
  - 敏感数据调用数据加密接口。
  - 使用加密接口的系统每日交换工作密钥。
  - 卡片认证调用专门认证接口。

验证重点：关键字段的服务端来源、完整性校验、密钥生命周期、防重放和日志脱敏。
