# 配置与投产变更规范

适用：配置、环境差异、投产包、版本发布、大表结构变更、回滚和投产验证。

## 配置不能错

**风险：中。检查手段：设计评审、投产评审、投产验证测试。**

- 测试与生产环境的数据库结构、应用逻辑和环境参数差异必须消除。
- 网络地址、文件路径、权限配置保持规则一致；投产前确认没有测试参数进入生产。
- 避免开发、测试环境的 IP、账号、密码、路径出现在生产部署包。
- 投产验证测试使用的版本必须与生产投产版本一致。
- 投产前使用自动脚本或对比工具扫描 `.yml`、`.properties` 等配置文件，并与生产配置清单逐项比对。

代码审查重点：配置来自环境变量或受控配置中心；默认值不指向测试环境；敏感值不进入仓库和镜像。

## 投产不夹带

**风险：高。检查手段：设计评审、投产评审。**

- 投产内容必须与已评审需求和设计一致，并通过全部研发管理流程。
- 禁止夹带故障修复、数据修复、非必要维护性功能或其他与需求/设计无关的内容。
- 投产前严格比对代码和产物，逐项确认变更来源、评审、测试和审批记录。

代码审查重点：本次 diff 可追溯到需求；没有顺手重构、隐藏开关、临时脚本或无关数据修改。

## 大表结构调整

- 记录数大于 100 万或数据量大于 10G 的表发生加字段、加索引等结构变更时，必须经过 DBA 和应用管理员评审。
- 评审至少覆盖：变更窗口、预计耗时、是否锁表、回滚方案、对应用的影响。
- 优先使用在线变更工具、低交易量窗口、临时表备份后切换等方式降低锁表风险。

## 投产前验证

- 技术和业务变更都安排业务人员验证，覆盖系统变更点与全链路。
- 联机交易验证完整；批量文件变化时跟批，定时任务变化时观察实际调度。
- 投产方案充分评审；投产中不得随意改变、省略步骤，遇到问题充分讨论并上报。
- 环境配置扫描发现开发、测试、localhost 等痕迹时，必须阻断投产。
- 投产前进行严格代码比对，确认没有因疏忽或夹带混入的内容。

交付证据应包含：配置差异清单、版本一致性、验证案例与结果、批量/定时任务结果、回滚方案和审批记录。
