# 关键正确性、业务连续性与批量规范

适用：账务、支付、记账、退款/撤销、交易幂等、批量任务、业务连续性，以及通用语言和脚本安全。

## 账务不能错

**风险：高。检查手段：设计评审、系统测试。**

- 账务类交易和批量系统必须具备完整的交易异常处理机制。
- 账务交易超时或状态未明时，禁止直接判定为失败。
- 同时具备状态查证和异步冲正能力时，账务未明阶段应避免交叉执行，防止最终状态确认不一致。
- 无法通过联机交易完成异常处理时，必须提供对账机制。
- 退款、撤销等反向交易必须具备防重和金额累计校验，且由系统承担校验，不能依赖人工保证。
- 需求和需求分析已明确的业务逻辑必须准确落实，不得以实现便利改变账务语义。

代码审查重点：交易状态机是否覆盖处理中、成功、失败、未明；重试与冲正是否互斥；幂等键、唯一约束、金额校验和补偿/对账是否闭环。

## 业务不能停

**风险：高。检查手段：设计评审、非功能测试。**

- 架构应采用均衡设计，避免单点故障导致业务暂停；投产变更必须提前设计回退和应急预案。
- 系统设计应规划替代流程，包括必要的业务人员手工替代方式。
- 序号依赖必须可靠，序列容量满足业务量；关键启动配置应在启动前检查，异常时给出明确提示。
- 证书有效期等时限字段必须具备提前预警。
- 关键字段的长度、枚举、非空和边界判断，应用层与数据库约束必须一致。

代码审查重点：无单点、可优雅启停、故障时替代路径可执行、配置错误可发现、应用校验不会比数据库更宽松。

## 批量不能晚

**风险：高。检查手段：设计评审、系统测试。**

- 批量程序自身必须具备“防重调”能力，不能只依赖批量调度框架。
- 批量系统必须支持重做或断点续作，并记录步骤/子步骤的开始、完成或失败状态。
- 涉及自动化入账的定时或批量任务，单笔业务记录异常时不得继续自动处理，应转人工处置。
- 多系统链路应在接入层、中间层和服务方分别实现防重，不允许只依赖单一节点。
- 根据业务要求登记异常后继续后续步骤，避免少量数据异常导致整体停批。
- 重做或续作时应具备无效数据清理、数据重载等能力。

代码审查重点：任务锁和交易防重同时存在；防重针对最终处理记录；状态包含中间态；并发触发多实例时只产生一笔有效业务；恢复过程可跳过已完成项且不会误重复处理。

## 开发语言基础设计

**风险：中。检查手段：CI 代码扫描、详细设计评审。**

- 变量使用前必须初始化；结构变量先声明结构再声明变量。
- 指针声明后初始化为 `NULL`；释放或使用前检查；释放后再次置为 `NULL`。[C 语言]
- 输入输出参数禁止使用 `strcpy`、`strcmp` 等不处理长度的函数，使用包含长度参数的函数防止内存溢出。
- 清理、移动文件或目录时参数使用全路径，禁止先 `cd` 到目录再执行相对操作。
- 打包备份必须使用相对路径，禁止把全路径打入 tar 包。

脚本审查重点：变量/资源初始化、长度控制、路径展开、通配符范围、当前工作目录变化，以及误删、覆盖、丢失文件的风险。
