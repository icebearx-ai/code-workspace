## 背景

Code Workspace 当前提供一个仅支持 Codex 的 `sync` 命令，用于重写 `.codex/config.toml` 中的托管区块。该命令名称没有表达它会改变目录授权；项目变更直接调用 Codex 专用逻辑；Claude 的 `.claude/settings.local.json` 尚未得到支持。如果继续通过条件分支增加 Agent 工具，将重复实现计划、确认、事务、验证和结果处理。

即使目标配置文件由 Code Workspace 修改，目录访问本质上仍属于用户授权。Code Workspace 的责任是展示请求的授权变更、准确实施该变更、保留无关配置、验证结果并进行报告；授权本身仍由用户负责。因此，Claude 授权不使用所有权元数据或人为构造的托管块，Code Workspace 也不会因为某个目录未注册为项目就推断应当撤销它。

现有 CLI 架构要求计划写入遵循“检查 → 规划 → 确认 → 开启事务 → 应用 → 验证 → 提交”的边界。因此，当同一命令同时触发项目注册表写入和 Agent 授权写入时，两者必须共享同一个计划和事务。

## 目标与非目标

**目标：**

- 使用语义明确的 `permissions apply` 替代 `sync`。
- 为所有选中工具展示一个与工具无关的授权计划，并只要求一次确认。
- 使用明确的目录 `grant` 和 `revoke` 操作表示授权变更。
- 在 Codex、Claude 以及未来工具之间共享编排、事务、验证、诊断和结果模型。
- 将文件格式及工具特有的冲突规则封装在已注册的权限适配器之后。
- 保留 Codex 与 Claude 中无关的用户配置。
- 使项目添加、删除和初始化与独立命令使用同一授权服务。
- 在不修改 CLI 契约或顶层结果结构的前提下支持未来工具。

**非目标：**

- 在 `.code-workspace/state.json` 中记录 Claude `additionalDirectories` 的所有权。
- 仅因为目录不存在于项目注册表中就自动撤销授权。
- 将用户额外授权的目录视为不健康状态。
- 让普通资产更新改变 Agent 授权。
- 将 hooks、commands、skills 或 monitoring 等无关 Agent 能力抽象到权限适配器接口中。

## 设计决策

### 1. 将授权建模为明确变更

核心请求使用明确操作：

```js
{
  grants: ["/absolute/project-a"],
  revokes: ["/absolute/project-b"]
}
```

`permissions apply` 从一个或多个选中工具缺失的已注册项目路径中推导 `grants`，但不生成隐式 `revokes`。`project add` 授予新增项目路径，`project remove` 撤销被删除项目路径。这样可以将授权后果追溯到具体用户操作，并避免从配置状态推断所有权。

曾考虑的替代方案：使每个工具的授权与 `projects[].location` 完全一致。该方案被否决，因为 Claude 的普通 JSON 数组无法区分用户自行写入的值和 Code Workspace 写入的值，强制对账可能在没有明确请求的情况下撤销用户授权。

### 2. 使用一个编排服务和注册式适配器

在 `src/core/permissions/` 下建立权限服务和适配器注册表。编排 API 负责跨工具行为：

```js
planPermissionChanges({ root, tools, grants, revokes })
applyPermissionPlan(plan)
inspectProjectPermissions({ root, tools, projects })
```

每个已注册适配器实现类似以下的稳定契约：

```js
{
  id,
  targets(root),
  inspect(root),
  plan({ root, current, grants, revokes }),
  apply(plan),
  verify(plan)
}
```

通用计划记录选中的工具、请求的操作、受影响目标、前置条件指纹、标准化后的逐工具变更以及验证预期。适配器负责解析和序列化，命令层不得直接读写工具配置。

曾考虑的替代方案：在现有 `syncPermissions` 函数中增加 Claude 分支。该方案被否决，因为它会把编排逻辑与两种文件格式耦合，并要求每增加一种工具都修改共享控制流。

### 3. 使用统一的交互与结果契约

CLI 按操作和目录展示合并后的计划，其中包含所有受影响的工具和文件，然后只请求一次确认。在非交互及 JSON 执行中，`--yes` 表示接受完整计划。如果计划不包含任何变更，命令无需提示并直接返回成功。

所有调用方接收统一的结果结构，其中包含请求的工具、请求的操作，以及每个工具的 `target`、`action`、`granted`、`revoked`、`unchanged` 和 `verified`。工具特有细节可以放入可选的嵌套 `details` 对象，但不能替代通用字段。

曾考虑的替代方案：分别确认和报告每个工具。该方案被否决，因为用户授权的是一个逻辑项目操作，分开确认会在共享事务启动前形成割裂的操作意图。

### 4. 将工具特有的存储行为封装在适配器中

Codex 适配器继续使用 `.codex/config.toml` 中带标记的区块，以避免修改无关 TOML。它只修改请求涉及的根目录：`grant` 添加缺失目录，明确的 `revoke` 删除匹配目录。因此，只包含授权补齐的 `permissions apply` 会保留托管块中已有的其他目录。现有非托管 sandbox 冲突继续作为 Codex 适配器特有的规划错误处理。

Claude 适配器解析 `.claude/settings.local.json`，保留所有无关 JSON 属性，只修改 `permissions.additionalDirectories`。当文件或包含对象不存在时创建它们；遇到不兼容的非对象或非数组结构时返回稳定诊断；对目录字符串去重；使用规范化的项目绝对路径。它不保存注释、托管标记或所有权元数据。

两个适配器都保留未删除条目的相对顺序，并以确定性顺序追加授权目录。明确的撤销只删除规范化后完全匹配的目录。

### 5. 将所有受影响文件作为一个经过验证的事务应用

规划发生在确认之前，并包含所有适配器目标；适用时还包含项目配置文件。每个目标都带有前置条件指纹，如果规划与应用之间文件发生变化，则以计划过期诊断失败。确认后，文件事务为所有目标创建快照，应用各适配器计划，并在提交前验证每项授权、撤销以及无关配置的保留情况。

任何应用或验证失败都会回滚所有受影响的权限文件；对于项目添加和删除，还会回滚 `.code-workspace/config.yaml`。多工具授权只要部分实施成功，顶层结果就不得报告成功。

### 6. 明确各命令的授权行为

- `permissions apply`：从显式 `--tools` 或持久化的 Workspace 工具选择中确定目标工具；授予缺失的已注册项目目录；不推断撤销；仅在存在变更时要求确认。
- `project add`：将项目注册表新增和选中工具的授权合并到同一个展示计划与事务中。
- `project remove`：将项目记录删除和针对选中工具的明确目录撤销合并到同一个展示计划与事务中。即使没有所有权元数据，也允许撤销，因为用户通过 Code Workspace 明确请求了删除。
- `init`：在初始化计划和确认中包含缺失授权；保留现有额外授权。重新运行初始化时遵循相同规则。
- `update`：普通更新和工具选择变更都不授予或撤销目录访问权限。新选中的工具缺少项目授权时，结果可以引导用户运行 `permissions apply`。
- `doctor`：按选中工具报告已注册项目缺失的授权。额外授权目录是允许的，不构成警告或错误。

### 7. 区分“支持的工具”和“具备权限能力的工具”

现有工具选择注册表描述 Workspace 资产支持的工具；权限支持则通过权限适配器注册表解析。如果选中的工具没有权限适配器，应返回稳定的“不支持该能力”错误，指出工具名称和补救方式，而不是静默跳过。这样，未来某个工具可以先加入资产安装，再实现权限集成，而无需修改权限编排 API。

## 风险与权衡

- [从 `config.yaml` 手工删除项目后，Claude 授权可能残留] → 文档明确：只有显式 `project remove` 撤销或用户直接编辑才能删除；`permissions apply` 始终只补授权。
- [用户可能期望 `update --tools` 自动配置权限] → 保持 update 授权中立，并返回可操作诊断，引导用户检查并运行 `permissions apply`。
- [Codex 托管块行为从“严格对齐项目注册表”改为“明确变更”] → 增加迁移和回归测试，证明只补授权时会保留额外根目录，而明确删除项目时只撤销对应根目录。
- [两个适配器可能采用不同的路径规范化规则] → 在编排层集中处理绝对路径规范化和去重，适配器只消费规范路径。
- [并发编辑可能被覆盖] → 在规划时为每个已解析目标计算指纹，并在第一次写入前拒绝过期计划。
- [回滚可能恢复用户在确认后并发修改的授权] → 在修改前立即执行过期检查，尽量缩短事务窗口，并准确报告回滚目标。
- [未来工具可能使用外部 API 而非本地文件] → 保持适配器目标和 effect 元数据可扩展，但本次变更仅支持可回滚的本地配置适配器。未来的外部适配器必须按照 CLI 架构契约声明保留的外部效果。

## 迁移计划

1. 引入适配器注册表以及与工具无关的权限计划和结果类型，同时将现有 Codex 行为迁入 Codex 适配器。
2. 添加 Claude 适配器和跨适配器事务测试。
3. 注册 `permissions apply`，更新帮助、补全和文档，删除 `sync` 注册项和分发路由。
4. 将项目添加、删除和初始化接入共享服务；保持 update 授权中立，并扩展 doctor 检查。
5. 将文档中的 `code-w sync` 补救说明和示例替换为 `code-w permissions apply`。
6. 运行架构、解析器、故障注入、完整测试和打包检查。

版本回退时恢复旧 CLI 和仅支持 Codex 的服务。由于每个命令都会为自身受影响目标创建快照并执行回滚，Workspace 文件仍然可恢复；本变更不会引入持久化的授权所有权结构。

## 待决问题

无。命令名称、旧别名删除、用户授权责任、Claude 存储策略、update 行为和扩展性边界均已在本变更中确定。
