## Context

`harden-cli-runtime` 已经解决语义解析、配置投影、统一结果、工具来源和主要文件回滚问题。剩余风险集中在少数失败边界：外部命令可能已产生副作用但尚未被记录，Schema 迁移步骤与旧语言兼容动作分别计算，以及参数解析失败时可能丢失已经识别出的命令路径。

本次设计以“发布前关闭高价值风险”为目标。完成后应停止继续抽象，预期把当前质量提升到约 92–94 分，而不是追求形式上的满分。

## Goals / Non-Goals

**Goals:**

- 外部命令在直接失败和后置验证失败时，都能诚实报告已发生或可能发生的 retained effect。
- init/update 输出一个包含 Schema 步骤和语言兼容动作的维护迁移计划。
- 已识别命令的解析错误保留命令上下文，关键失败具有稳定代码和可操作证据。
- 为不同风险等级的写操作明确最小充分保护，不强制使用同一种事务机制。
- 用针对性故障注入和契约测试覆盖新增行为。

**Non-Goals:**

- 不回滚全局 npm 安装、整个 `node_modules` 或任意第三方命令输出。
- 不扫描或快照完整工作区来追踪所有未知文件。
- 不依赖解析第三方命令的非结构化自然语言输出。
- 不引入第三方参数解析器、事务框架、事件总线或迁移框架。
- 不为了缩短文件或统一风格拆分 `executeProject()` 等现有处理器。
- 不要求一次性为所有历史错误补齐最细粒度代码，只处理本变更触达的高风险路径。

## Decisions

### 使用小型 retained-effect 附加器，而不是通用效果系统

增加一个只负责规范化和合并 `error.details.effects.retained` 的小型辅助函数。效果记录至少包含 `kind`、`status`、目标范围和可用证据；`status` 只使用 `applied` 或 `possibly-applied`，避免在证据不足时宣称确定结果。

- 全局 OpenSpec 安装：一旦执行安装命令，后续版本验证失败也要记录全局包效果，并附上重新检测到的版本。
- Workspace dependencies：只比较 `node_modules` 和 lockfile 在命令前后的存在状态，不遍历或哈希整个依赖树。命令失败或声明依赖验证失败时，报告实际出现或可能被修改的路径。
- 上游 `openspec init`：直接失败和退出码为 0 但后置条件不满足采用同一报告路径。枚举已创建的必需目标，并明确该列表不是第三方输出的完整清单。

选择该方案是因为当前只有三个明确的外部效果边界。建立通用事件溯源、可插拔补偿器或完整文件清单会显著扩大维护成本，却不能真正让第三方命令可回滚。

### 聚合维护迁移计划，不扩建通用迁移引擎

保留现有纯配置 `CONFIG_MIGRATIONS`，新增一个维护计划组合器，将以下信息汇总为一个结果：

- Schema 版本步骤。
- 是否需要补齐 `workspace.language`。
- 语言来源是显式 CLI、当前配置、旧 state、OpenSpec context 还是默认值。
- 发生冲突时的稳定诊断和修复命令。
- 计划会写入的配置/state 目标。

只读投影继续直接读取受支持旧配置且不生成写入。init/update 使用组合计划并在现有文件事务内提交。这样可以让迁移输出真实可审计，同时避免为了两个旧版本建立跨资源迁移框架。

### 解析错误通过错误详情传递命令路径

命令解析完成后，后续参数错误在 `WorkspaceError.details.command` 中携带规范化命令路径。`main()` 捕获解析异常时从该字段填充结果信封的 `command`。真正无法识别的命令仍保持 `command: null`。

不改变 parser 的公开成功返回结构，也不引入部分解析结果类型，以减少兼容面。

### 写入安全采用三级模型

1. **单文件原子写**：继续使用 atomic write，并在函数内部验证目标内容；不套多文件事务。
2. **多文件工作区写**：继续使用 `createFileTransaction()`，报告 restored、removed、retained 和 rollbackFailures。
3. **外部效果**：检查退出码、执行命令专属后置验证、记录不可补偿效果；不得声称整体事务回滚。

因此 `sync` 不为形式一致而引入事务，只需保证权限文件的原子写和写后验证。init/update/project 保持当前边界，不再重排整个命令生命周期。

### 测试围绕已确认缺口，而不是建立穷举矩阵

新增测试只覆盖：外部命令部分成功、后置验证失败、旧配置的交互式与 `--yes` init、已识别命令解析错误、关键 JSON 失败信封和单文件写后验证。现有已经稳定的每个文本输出不重复快照。

## Risks / Trade-offs

- **效果记录可能给出过度确定的结论** → 证据不足时使用 `possibly-applied`，并区分已验证工作区回滚与外部保留效果。
- **依赖目录变化难以精确枚举** → 只报告 `node_modules` 和 lockfile 的范围级效果，不承诺包级差异。
- **迁移计划组合器与现有语言解析重复** → 复用现有语言来源函数，组合器只负责步骤与来源编排，不复制解析规则。
- **新增错误字段影响严格消费者** → 保持现有信封和字段不变，仅向 diagnostics/effects 增加可选字段。
- **测试仍非全命令笛卡尔积** → 以注册表、共享 renderer 和代表性命令测试公共契约，只为存在特殊输出路径的命令增加独立测试。

## Migration Plan

1. 先实现 retained-effect 附加器并补三个外部命令失败测试，确保不改变成功路径。
2. 聚合维护迁移计划，接入 init/update，并增加旧配置交互式与非交互测试。
3. 补解析错误命令上下文和权限写后验证。
4. 运行全量测试、Patch 一致性、发布包 dry-run 和 OpenSpec 严格校验。
5. 当上述验收通过后停止；不继续拆分 handler 或推广新的抽象。

若需要回退，可分别撤销效果报告、迁移组合器和解析错误增强；现有配置格式与成功结果不需要数据回滚。

## Open Questions

无阻塞问题。效果记录字段名称应尽量复用当前 `effects.retained`，避免引入第二套失败载荷。
