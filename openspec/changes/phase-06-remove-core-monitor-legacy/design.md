## Context

Monitor 扩展在第五阶段成为默认路径后，核心仍会暂时保留旧实现以保证回退。第六阶段只处理已证明无必要的兼容代码，属于产品清理和破坏性变更，不应与扩展机制建设混在一起。

## Goals / Non-Goals

**Goals:**

- 在明确门槛满足后删除 Monitor 专用核心配置、CLI、业务源码、资源和桥接。
- 保留扩展版 Monitor 的公开行为和生命周期。
- 给出公共 API 和命令的 deprecation/removal 证据。

**Non-Goals:**

- 不重新设计扩展运行时协议。
- 不删除扩展安装状态、扩展配置或用户运行期数据。
- 不改变 Monitor Session 业务规则。
- 不在未满足兼容门槛时提前实施。

## Decisions

### D1: 清理有硬性准入门槛

只有同时满足默认切换已完成、至少一个兼容发布周期无阻断迁移问题、扩展业务测试对等、回滚手册已更新、公共 API 已达到 deprecation 期限时，才允许进入本阶段。任何一项不满足都停止实施。

### D2: 分面删除而不是一次删除

按顺序移除旧 CLI 路由、managed Hook、核心配置域、公共导出、业务源码和打包资源。每一面都具有独立验证；出现问题时只回滚对应提交，不回滚扩展安装状态或用户配置。

### D3: 行为和实现分离

`monitor-session-lifecycle` 的既有业务要求继续由扩展满足；删除核心源码不产生新的 Monitor 行为需求。只有命令、配置和公共 API 的移除需要迁移说明。

### D4: 不做隐式数据清理

删除核心实现不得删除 `.code-workspace/config-monitor.yaml`、扩展状态、运行期用户数据或用户 Hook。卸载和清理必须通过显式扩展生命周期操作完成。

## Risks / Trade-offs

- 用户仍依赖核心公共 API → 通过 deprecation、版本说明和可搜索的迁移错误降低风险。
- 删除后发现业务不兼容 → 保留扩展行为测试和回滚到上一发布版本的能力。
- 清理范围过大难以定位回归 → 每个删除面单独提交、单独测试、单独回滚。
- 兼容代码被误认为无用户 → 必须用发布统计、文档访问或显式迁移证据确认，而非主观判断。

## Migration Plan

1. 验证准入门槛并冻结扩展行为基线。
2. 发布包含破坏性移除说明的新主版本候选。
3. 分面移除核心实现，每步执行完整检查。
4. 保留扩展路径和显式数据保留语义。
5. 回滚时恢复对应核心面，不修改用户扩展状态和配置。

## Open Questions

- 兼容别名和旧公共 API 是保留一个主版本，还是绑定明确日期；必须在第五阶段归档前形成可验证政策。
