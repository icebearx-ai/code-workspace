## Context

第一阶段提供通用运行时 CLI，但扩展尚无用户可修改的配置载体。把扩展字段放入核心 `config.yaml` 会让核心解析、迁移和诊断扩展业务；完全由扩展自行选择绝对路径又会破坏 Workspace 可移植性、事务和保留语义。

## Goals / Non-Goals

**Goals:**

- 为扩展提供 Workspace 内、固定可发现、用户可编辑的配置文件。
- Host 管理路径、创建时机、原子写入、升级保留和卸载保留。
- 扩展管理配置 schema、默认内容、校验和业务解释。
- 配置错误只影响对应扩展，不阻断无关核心命令。

**Non-Goals:**

- 不迁移 `config.monitor`。
- 不把扩展配置并入核心 `config.yaml`、state 或 config projection。
- 不在本阶段强制所有扩展使用 YAML；首版生命周期支持通用文件声明，默认模板格式由扩展提供。
- 不提供远程配置同步或密钥管理。

## Decisions

### D1: 配置文件归 Workspace 控制面，版本目录只提供默认模板

首选路径为 `<workspace>/.code-workspace/<declared-config-file>`。manifest 声明稳定的相对文件名和默认模板，Host 校验路径不能逃逸 Workspace 控制目录。用户可以修改该文件，扩展版本升级不得把它当作 exclusive artifact 漂移。

### D2: Host 只做通用文件生命周期

Host 负责安全路径校验、首次创建、原子写入和事务登记；它不解释字段、不提供 Monitor 专用 normalization。扩展通过运行时 context 获得配置文件路径，并自行读取和校验。

替代方案是核心暴露 `readExtensionConfig(id, defaults)` 并由核心做业务默认值。该方案会让核心理解扩展字段，因此拒绝。

### D3: 升级和卸载默认保留

安装时仅在文件不存在时创建默认内容；已存在文件绝不覆盖。升级保留用户文件。卸载只删除扩展制品和 Hooks，默认保留配置文件与运行期数据；只有未来显式声明 `removeData` 的操作才可删除，且需要单独确认。

### D4: 配置错误隔离

配置缺失、解析失败或字段非法只导致对应扩展 CLI/observer 不可用或被禁用，并返回扩展级诊断。Host 发现、核心 init/update、其他扩展和其他命令不得因该配置错误失败。

## Risks / Trade-offs

- 文件格式过窄会限制后续扩展 → Host 只处理字节和事务，扩展可自行定义文本格式。
- 配置保留可能积累陈旧文件 → 卸载结果明确报告保留路径，后续可设计显式清理命令。
- 用户错误无法被 Host 理解 → 扩展负责结构化诊断和 remediation，Host 只透传。
- 配置可能包含敏感内容 → 默认模板不得包含真实凭证，日志和状态不得复制配置正文。

## Migration Plan

1. 增加 manifest 声明和配置文件路径模型，使用独立 fixture 扩展验证。
2. 把创建和保留纳入现有安装/升级/卸载事务，但不改变任何已有扩展。
3. 验证损坏配置不阻塞核心命令。
4. 回滚时停止创建新配置并移除协议支持；已经创建的用户文件必须保留。

## Open Questions

- 默认文件名是否固定为 `config-<extension-id>.yaml`，还是由 manifest 声明任意安全文件名；需要在与文件名冲突和用户可发现性之间选择。
- 默认模板采用内联对象还是扩展包内模板文件；后者更利于多行注释，但增加 staging 复杂度。
